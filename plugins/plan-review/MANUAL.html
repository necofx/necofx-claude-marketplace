Plan-First Multi-Agent Workflow

Ticket → researched plan → atomic phases in parallel rounds → one agent per phase → reviewable hand-off. Every step's output is a file, so no step depends on a conversation still being open. Stack-agnostic.

The five steps

1
Create the master plan /create-master-plan 412

Fetches the ticket + cited documents + local docs, interviews you on the gaps → issue.specs, master-plan.md

2
Decompose into rounds /decompose-plan docs/plans/GH-412

Atomic phases, grouped into parallel rounds, file-conflict checked → phases/, tasks.md, execute-plan.md, handoff.md

3
Execute paste execute-plan.md into a fresh conversation

Coordinator dispatches one agent per phase, whole round at once, advances only when the round is green

4
Review and fix /code-review

Findings on the branch diff → fix → review again

5
Close out the documents —

Finish tasks.md and handoff.md; fold anything durable into the project's rules

Steps 1, 2 and 3 each go in their own conversation — step 3's coordinator needs a near-empty context window, and step 1 ends with a large research payload in yours.

1 · Create the master plan

/create-master-plan 412

Takes a GitHub issue number by default, or a tracker key or URL. It does four things:

Phase of the stepWhat happens
FetchThe source comes from a detection ladder in references/source-adapters.md — GitHub by default, Jira and Linear as profiles, free-form text as the fallback — and every adapter normalises into one record, so no later step knows which one ran. It pulls the issue with all fields, comments and attachments; up to 5 linked items (parent epic → blocks → relates-to → sub-tasks) and 3 cited documents, quoted in full rather than linked. On GitHub, a referenced merged PR's file list is the highest-value field in the whole ingestion.
Scandocs/**/*.md exhaustively — no directory excluded, no cap — for the ticket key, component names and distinctive nouns. Long output is expected; it surfaces the internal doc nobody remembered.
Detect stackTicket text → root markers (*.sln, package.json, *.dproj…) → ask. Mixed stacks get a layer-to-stack map. This drives every build command, test framework and rule citation downstream.
InterviewStructured questions over a coverage matrix: goal, constraints, scope boundary, implementation, UI/UX, edge cases, tradeoffs, acceptance criteria, testing, validation gates. Skips anything already answered; grounds each question in the code first.
The interview is the step that decides quality

Everything downstream is derived from it. A vague requirement here becomes five agents confidently building the wrong thing in parallel at step 3. Q&A is appended to issue.specs under ## Interview Notes, so a later run sees what was already settled.

Stops at master-plan.md. Never decomposes, never writes back to the tracker.

2 · Decompose into rounds

/decompose-plan docs/plans/GH-412

Phase — one atomic unit for one agent. Single-focus (an "and" in the goal means split it), independently verifiable, 30 min – 3 h, dependencies named not implied.
Round — a set of phases that run in parallel. Rounds run sequentially. Round 0 is usually one foundation phase, round 1 the wide fan-out, the last round integration and verification.

File-conflict matrix

What makes parallelism safe. For every multi-phase round, it lists each phase's create/modify files and verifies no two touch the same one. Unavoidable overlaps get an explicit coordination rule in tasks.md: which phase edits first, how the second rebases.

Skill matching

Phase files list the skills their agent must invoke. Rather than guessing names, the skill inventories what actually exists — runtime-active, then .claude/skills/**/SKILL.md, then user-global — tags each with stack/domain/verb hints, and scores:

score = 3x(stack) + 2x(domain) + 1x(verb) + 2 if runtime-active
        - 5 if skill and phase have conflicting stacks
recommend at score >= 3, cap 4 per phase

No match means only the always-on skills plus an explicit note — never a padded list. A missing specialist the phase obviously needs is recorded in tasks.md so you can install it or accept the gap.

3 · Execute

Open a fresh conversation, paste the Coordinator Prompt from execute-plan.md. The coordinator then loops:

  1. Read master plan, tasks.md, every phase file — know the whole shape first.
  2. Dispatch every ready phase in the round in a single message, one Agent call each, so they genuinely run concurrently.
  3. Wait for the whole round to reach completed.
  4. Run the full build + test gate to confirm the phases integrate; write a round summary into tasks.md.
  5. Surface a batched commit command and advance without waiting for you to run it.

Each agent works only from its phase file, and may edit only its own row in tasks.md.

TDD shape inside a phase

Locate the surface area (one codegraph explore call on an indexed repo, a search loop otherwise) → one failing test → confirm it fails → minimum implementation → confirm it passes → edge cases one at a time → full build and test gate → TDD proof: deliberately break the implementation, confirm the tests that should fail do fail, restore.

That last step is what separates tests that verify behaviour from tests that merely execute code.

Phases never commit

Each leaves a clean, tested tree and writes (pending batch). The coordinator batches commits at end-of-round. Five agents finishing unpredictably would otherwise produce interleaved partial commits nobody can review — and per-phase approvals would stall the run constantly.

4–5 · Review, fix, close out

/code-review

Reviews the branch diff. Takes an effort level (low/medium = fewer, higher-confidence findings; high+ = broader, includes uncertain ones). --fix applies findings; --comment posts them inline on the PR. For a second opinion:

AgentAngle
code-reviewerQuality, security, maintainability
architect-reviewerLayering, SOLID, dependency direction, does it make future change harder
security-auditorOWASP, auth flows, input validation, secrets
Findings are claims, not verdicts

Some are wrong. Verify each against the code before changing anything — accepting a wrong finding costs more than missing a marginal one.

Peer review with Codex optional

Everything above happens in the session that did the work. When you want a reviewer that never saw the plan being written, the plan-review skills generate a self-contained review prompt and hand it to an external agent — the plan before it is built, or the changeset against the plan afterwards:

/plan-review-prompt            # the plan — run it after step 2, before you execute
/plan-implementation-review    # the changeset against the plan — run it here

Each prints the prompt, offers to save it, and then offers to run it. Say yes and it executes this from the repo root:

codex exec --sandbox read-only ${CODEX_OPENROUTER_MODEL:+-m "$CODEX_OPENROUTER_MODEL"} \
  -o <report>.md < <prompt>.md

read-only is the point — a review must not touch the tree it is judging — and -o captures the report verbatim, so you read the reviewer's own words rather than a retelling of them. The model is never hardcoded: export CODEX_OPENROUTER_MODEL to pick one — a reviewer is exactly where you want a different model from the one that wrote the code — and leave it unset to fall back to your Codex config. Both offers are opt-in: decline either and you still have the prompt, which is the deliverable. Any capable reviewer with read access to the repo will take it; Codex is simply who it was written for.

Don't edit while it runs

The prompt makes the reviewer regenerate the diff live rather than trust the embedded snapshot, so a changeset review takes minutes and anything you change meanwhile produces findings against code that no longer exists. Start it, then work outside the repo.

Nothing downstream waits on this. /code-review covers the ordinary case; reach for a peer review when the question is whether the code built what the plan specified — which a diff review cannot judge, because judging it requires the plan. Note that the CLI's own codex review --base main is the former, not the latter: it knows nothing about your plan.

Then close the loop: real commit SHAs and the final summary in tasks.md; every section of handoff.md filled — especially deviations from the plan, which is where reviewers spend their attention and where unexamined assumptions hide; and anything durable folded into .claude/rules/ rather than left in a plan folder nobody reopens.

Token economy: CodeGraph

Every agent spends its first tokens rediscovering the codebase: grep a symbol, get a file list, read those files whole to find a few signatures, repeat per phase. The answer is a few hundred bytes; the cost is hundreds of kilobytes.

CodeGraph keeps a SQLite graph of every symbol, edge and file, so one call returns the relevant symbols' verbatim line-numbered source, the call paths between them, and a blast radius of what depends on them. Sub-millisecond reads; the index lags writes by about a second.

Resolving one method on a 7,889-file C# repo — where it's declared, who implements it, who calls it:

ApproachInto context
codegraph explore "<symbol>" — one call25 KB
grep -rl then reading the 9 matched files649 KB

~26× less, for a strictly better answer — grep-and-read gives no call paths, no dependents, and cannot follow a call through an interface, a DI container, a callback or a React re-render. That's a correctness argument too: a phase that missed a caller because the call went through an interface produces a green build and a broken runtime. One symbol, one repo — indicative, not a benchmark.

Where the workflow uses it

StepUse
1 · interviewcodegraph_explore to ground questions before asking
2 · dependency graphimpact / callers to check the plan's claims against the code
2 · conflict matrixexplore to resolve each phase's real Modify list — the registration file the plan forgot is the usual conflict source
3 · phase step N.1explore once per phase instead of the search loop — the largest repeated cost in a run
3 · scoped testsaffected <changed-files> to find the tests a change reaches

All of it is conditional on a .codegraph/ directory existing. Nothing breaks on an unindexed repo — it just costs more.

Commands

CommandReturns
explore "<symbols or question>"The main one: source + call paths + blast radius, one shot
node <symbol|file>One symbol's source + caller/callee trail, or a file with line numbers and dependents
callers / callees <symbol>Who calls it / what it calls. Run callers before changing any signature
impact <symbol>What a change reaches, to a given depth
affected <files…>Test files a change reaches. --quiet for bare paths
query <search>Symbol search — cheapest way to confirm a name exists
status / sync / filesIndex stats, force a sync, file structure from the index

codegraph_explore and codegraph_node are the MCP equivalents, identical output.

Two boundaries

It indexes code, not prose — step 1's docs/**/*.md scan stays a text search.
Indexing is the user's decision — the skills never run init themselves. It builds a database of your full source (410 MB on the repo above) and ships telemetry enabled by default.

3 · The ticket source GitHub by default

Nothing to install. The default adapter uses the gh CLI — confirm gh auth status is happy and you are done. Plan ids are GH-<issue number>.

Jira or Linear instead? Connect the matching MCP server and declare the source in the planning repository's CLAUDE.md:

claude mcp add --transport http atlassian https://mcp.atlassian.com/v1/mcp
claude mcp list          # expect: atlassian - Connected

First use opens a browser for OAuth; you need read access to the project and the Confluence spaces your tickets cite. Tell the skill your site host — the your-org.atlassian.net part of a ticket URL — since it cannot discover it. If both an Atlassian and a Linear MCP are connected, a bare ACME-1234 matches two adapters and the skill will ask which you meant; the CLAUDE.md line is what stops it asking every time.

No tracker at all? Paste the requirement and the free-form adapter takes it, or hand-write issue.specs from references/issue-specs-template.md and start at /decompose-plan. Steps 2–5 have no tracker dependency.

5 · CodeGraph strongly recommended

# A real global install — the MCP entry invokes the bare `codegraph` command,
# so an npx-only setup silently fails to start the server.
npm install -g @colbymchenry/codegraph

# -y is required: the installer is interactive and otherwise hangs.
# Agent ids: claude, cursor, codex, opencode, hermes, gemini, antigravity, kiro
# — it is `claude`, NOT `claude-code`.
codegraph install -y -t claude -l global

# Telemetry ships ENABLED. Turn it off before indexing proprietary code.
codegraph telemetry off

cd /path/to/your/repo
codegraph init && codegraph status

Initial index ≈2.5 min for 7,900 files; a few hundred MB at .codegraph/codegraph.db, which self-gitignores. Auto-syncs afterwards; codegraph sync . forces it. Keep the CodeGraph block at the top of CLAUDE.md — it's what points agents at the graph before they grep; delete it in repos you don't index. Note install also writes that block into your global ~/.claude/CLAUDE.md. Remove everything with codegraph uninstall + uninit <path>.

6 · Install the template

Copy template/.claude/ into your repo root (merging with any existing .claude/), and template/CLAUDE.md to the root — or merge its Planning workflow and Coding rules sections into the one you have. Delete the agents you won't use.

Skill discovery is strict

A project skill is found only at .claude/skills/<name>/SKILL.md, exactly one level deep — a grouping subfolder makes it silently invisible. On Windows also check core.symlinks: symlinked skill directories otherwise land as plain text files and the skill vanishes with a clean git status.

7 · Point it at your plans directory optional

Plan folders default to docs/plans/<TICKET-ID>/. To put them elsewhere, say so in the planning repository's CLAUDE.md — and give decompose-plan and the review skills the same value, since all three address the same folder and a mismatch means step 2 cannot find what step 1 wrote.

There are no {{TOKEN}} placeholders left to substitute; the defaults are baked in and the tracker lives behind the adapter layer.

8 · Decide the git policy

Shipped default: settings.json denies every git write and rules/git-workflow.md documents why — the coordinator emits commit commands as text for a human to run. To let agents commit, change both files: the rule states intent, the deny list is the actual gate.

9 · Write your rule files

The highest-leverage remaining work, and the one thing nobody can ship for you. Phase files cite .claude/rules/*.md by path; with none, every agent falls back to generic best practice and your conventions erode one phase at a time. Start with the three that catch the most review comments — usually code style, testing, error handling.

10 · Smoke-test

Run all five steps on a small, well-understood ticket. You're checking plumbing, not ambition: the fetch connects, the interview asks sensible questions, the phases are ones you'd have written yourself, the coordinator dispatches in parallel.

When it goes wrong

SymptomCause and fix
Skill isn't foundMust be at .claude/skills/<name>/SKILL.md, exactly one level deep. Check for a grouping subfolder; on Windows check core.symlinks.
Ticket fetch failsOn GitHub: gh auth status, and confirm the issue number exists in this repository. On Jira or Linear: claude mcp list, re-authenticate, and confirm the site host is the bare host — no https://, no path.
Vague or overlapping phasesAn underspecified master plan. Don't patch the phases — sharpen the plan. Inferred sections are flagged in tasks.md § Coordination Notes; read those flags.
Same-round file conflictThe matrix missed it. Move one phase to the next round, or add an explicit coordination rule naming who edits first.
Coordinator dispatches sequentiallyAll phases in a round must go in one message with one Agent call each. Sequential dispatch forfeits the entire point of rounds.
Agent claims done, build is brokenThe verification gate was skipped. Check the phase's Verification section names your real commands and that superpowers:verification-before-completion resolves.
A phase goes silentAsk it to summarise and update tasks.md. If genuinely blocked it should set Status = blocked and fill Active blockers; the coordinator then re-dispatches, resolves, or drops it.
Agents ignore your conventionsNo rule files, or the phase files don't cite them. Check a phase's Documents to Read — an empty list means there was nothing to cite.
Agents still grep instead of using CodeGraphNo .codegraph/ directory (every CodeGraph instruction is conditional on it), the CodeGraph block is missing from CLAUDE.md, or the server isn't running.
codegraph MCP won't startAlmost always an npx-only setup — it must be on PATH: npm i -g @colbymchenry/codegraph. Confirm the agent id was claude, not claude-code.
CodeGraph returns stale symbolsThe watcher lags ~1s. codegraph sync .; codegraph unlock clears a stale lock.

Why it's shaped this way

DecisionReason
Rounds, not a dependency queueA queue is faster but leaves an arbitrary subset of phases in flight against a moving codebase. Rounds buy a barrier where the full suite runs before anything else starts — without it, a round-1 mistake is found by five round-2 agents at once.
Commits batched, never per-phaseParallel agents produce interleaved partial commits nobody can review, and per-phase approval stalls the run on every finish.
Rules cited, never copiedA copied rule drifts from the real one within weeks — and then agents follow the stale copy with total confidence.
The interview isn't optionalThe tracker holds what was written down. The real constraint, the rejected alternative, the reason it matters — none of that is in the tracker. Skipping it yields a plan that is fluent, complete-looking and subtly wrong.
One conversation per stepStep 1 ends with a large research payload in context; step 3's coordinator needs room for the whole plan plus every agent's reports. The artifacts on disk make the split free.

Extending it

  • New tech stack — add a profile to tech-stack-profiles.md in both skills (root markers, build/test/scoped-test commands, test framework, assertion and mocking libs, conventions location, commit convention). Add its keywords to skill-matching-heuristics.md. No SKILL.md edit needed.
  • New specialist agent — drop it in .claude/agents/ with frontmatter. The description is what the matcher scores against, so name the stack and domain explicitly.
  • Different tracker — add a profile to create-master-plan/references/source-adapters.md with its row in the detection ladder, and do not touch SKILL.md. Every adapter normalises to the same record, and everything downstream reads that record rather than the tracker. If a new tracker seems to need a change in the skill body, the record is missing a field and adding the field is the fix.
